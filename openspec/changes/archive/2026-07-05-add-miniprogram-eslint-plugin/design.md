## Context

仓库内已经存在 `packages/wxml`，提供了基于 `@typescript-eslint/utils` 的规则实现、规则导出、测试与文档生成方式。`packages/miniprogram` 当前只有占位的 `package.json` 与 `LICENSE`，还不具备可构建、可测试、可发布的插件结构。

这次变更既要补全插件包基础设施，也要落地首条具备自动修复能力的规则。规则目标不是泛化所有对象字面量的空行风格，而是仅处理小程序 `Page`、`Component`、`Behavior` 调用时传入对象中的约定成员，以及部分二级配置对象中的第一层成员。实现上需要兼顾源码注释、额外空行和首个成员前空行清理，避免修复结果破坏原有注释归属。

## Goals / Non-Goals

**Goals:**

- 将 `packages/miniprogram` 补全为与 `packages/wxml` 一致的 ESLint 插件包结构
- 提供一条默认可修复的规则，覆盖 `Page`、`Component`、`Behavior` 顶层成员间空行，以及指定二级对象内第一层成员间空行
- 明确注释与空行的处理规则，使自动修复结果稳定、可预测
- 明确插件仅支持 ESLint v9+ flat config，并通过 `recommended` 直接提供可消费的 flat config
- 为规则补齐测试、文档、推荐配置与包发布所需元信息

**Non-Goals:**

- 不在本次提案中设计第二条及以上小程序规则
- 不扩展到任意对象字面量、第三层及更深层级对象的空行规范
- 不为 `.eslintrc`、legacy config 或 ESLint v9 之前的配置系统提供兼容层
- 不调整现有 `packages/wxml` 的行为或抽象出跨包共享 fixer 框架，除非实现时发现存在明显重复且成本很低

## Decisions

### 1. 以 `packages/wxml` 为包结构基线补全 `packages/miniprogram`

`packages/miniprogram` 将补齐 `src/index.ts`、`src/rules/index.ts`、规则文件、测试文件、README、docs、构建配置与发布脚本，保持与 `packages/wxml` 一致的仓库约定。这样可以减少新的维护模式，并复用现有 lint、typecheck、publint、`eslint-doc-generator` 工作流。

备选方案：

- 直接用根目录配置临时实现规则，不创建完整包。缺点是无法形成独立插件，也不符合需求中的包信息完善目标。
- 用 Yeoman 重新生成整个包。缺点是当前目录已存在占位内容，且生成结果仍需较多手工调整，不如按现有包约定直接补齐更可控。

### 2. 规则仅匹配 `Page`、`Component`、`Behavior` 的直接调用对象

规则会从 `CallExpression` 入手，仅在 callee 是这三个全局 API 且首个参数为对象字面量时生效。顶层统一检查对象第一层成员；若是 `Component` 或 `Behavior`，再针对白名单字段对应的对象字面量检查其第一层成员。

备选方案：

- 基于变量引用或工厂包装做更宽松匹配。缺点是复杂度显著上升，而且会引入误报。
- 对所有对象字面量按键名启发式匹配。缺点是缺少语义边界，容易污染普通业务对象。

### 3. 自动修复采用“成员边界重写”而非逐行增删空行

修复时会基于 `SourceCode`、成员节点范围与紧邻注释范围，计算相邻成员之间应存在的标准分隔片段，并用 fixer 重写分隔区域，使结果归一为：

- 普通相邻成员之间恰好一个空行
- 若下一成员前存在连续注释，则上一个成员结尾到第一条注释前恰好一个空行
- 若成员末尾带有行内注释，则该注释视为当前成员的一部分，仍然按普通相邻成员之间的空行规则处理
- 第一个成员前的所有空行移除，但保留注释本身
- 最后一个成员后的所有空行移除

规则报告不会把整个对象折叠成单个错误，而是对每个独立的空行问题分别报告。报错位置应尽量贴近实际需要调整的位置，例如下一个成员、相关注释块或闭合花括号，这样用户看到的行号会更接近真实修复点。

这种方式比基于行号增删换行更稳，因为它能同时处理多空行、单行注释、多行注释以及已有空行混合出现的情况。

备选方案：

- 依赖 token 逐个插入/删除换行。缺点是要处理的边界较多，尤其在注释参与时容易出现重复修复。
- 直接格式化整个对象文本。缺点是改动范围过大，风险高，也更容易影响无关空白。

### 4. 规则文档、推荐配置与自动修复能力在首版就一并提供

`src/index.ts` 会暴露插件对象与 `recommended` 配置，首版推荐配置默认启用 `miniprogram/padding-line-between-members`。该 `recommended` 配置直接面向 ESLint v9+ flat config 消费，不提供 legacy config 兼容导出。为了降低使用门槛，`recommended` 将采用“自带插件注册”的 flat config 形式，也就是配置本身包含 `plugins: { miniprogram: plugin }` 与默认规则级别，用户可以直接在 `eslint.config.js` 中展开使用，例如 `export default [...miniprogram.configs.recommended]`。规则元信息需要明确其为可自动修复规则，以便 ESLint 在 `--fix` 流程中应用该规则的 fixer。文档通过 `eslint-doc-generator` 生成，保证与其他包一致，并让使用者可以直接从 README/规则文档了解 flat config 下的接入方式与修复行为。

备选方案：

- 先只发布规则，不提供推荐配置。缺点是用户接入路径更长，也与现有插件体验不一致。
- 同时提供 legacy config 兼容导出。缺点是超出本次支持范围，并会增加文档、测试和导出维护成本。
- 只导出插件对象，让用户自行注册 `plugins` 并逐条开启规则。优点是更灵活；缺点是接入更啰嗦，也更容易出现命名空间或规则名配置错误。

### 5. 测试以 fixer 输出和配置可用性为中心

测试不仅要覆盖“是否报错”，还要覆盖“修复后是否得到唯一、稳定的输出”。对于所有核心格式化场景，`RuleTester` 用例都应优先断言 `output`，并对多轮修复收敛、幂等行为以及成员末尾行内注释场景提供专门样例。除此之外，还需要提供针对 `recommended` 的 flat config 冒烟测试，确认插件导出结构和默认启用的规则名可以被 ESLint v9+ 直接消费。

备选方案：

- 只验证报错数量和 messageId，不验证 fixer 输出。缺点是无法保障自动修复行为符合 spec，尤其容易遗漏尾部空行、注释边界和多轮修复收敛问题。
- 只在手工示例中验证 `recommended`。缺点是发布后更容易出现导出路径、规则名或配置结构错误。

## Risks / Trade-offs

- `[注释绑定判断复杂]` → 通过测试覆盖单行注释、多行注释、首成员前注释、注释后保留空行等场景，确保 fixer 不挪动注释文本
- `[仅白名单二级字段生效]` → 在文档中明确规则范围，并让 spec 固化哪些字段必须检查，避免后续实现漂移
- `[自动修复可能与其他格式化规则交互]` → 让修复结果始终收敛到单一空行形式，并在测试中加入重复执行 fixer 的幂等性验证
- `[fixer 输出与设计预期不一致]` → 以 `output` 断言作为主要测试方式，并单独覆盖尾部空行、行内注释和多轮修复收敛场景
- `[报错位置不利于定位问题]` → 对每个独立空行问题分别 report，并让错误节点尽量贴近实际修复位置
- `[recommended 配置发布后不可用]` → 增加 flat config 冒烟测试，直接验证 `recommended` 默认启用目标规则
- `[包结构补全涉及多个文件]` → 复用 `packages/wxml` 的目录约定与脚本，尽量减少新模式
